# Russh — 架构与前端设计方案

> 版本：v1.0 | 日期：2026-05-30

---

## 1. 架构决策与权衡

### 1.1 为什么选 Tauri 而不是纯原生

项目选择 Tauri v2.0 作为桌面容器，这是一个**有意识的权衡**：

| 维度 | 纯原生（Swift+AppKit / C#+WPF） | Tauri v2.0 |
|------|------|------|
| 原生感 | 完美，无泄漏 | 接近原生，但窗口/菜单/材质有抽象泄漏 |
| 跨平台代码复用 | 需写两套 UI | 一套 React 代码库，两个平台共享 |
| 开发速度 | 慢，每个平台独立迭代 | 快，热重载，一套代码 |
| 内存基线 | macOS ~90MB / Windows ~130MB | 略高，但仍在合理范围 |
| 团队要求 | 需要 Swift + C# 两套技能 | Rust + React/TS，技能栈统一 |

**结论**：对于一个 SSH 客户端，Tauri 的权衡是值得的。我们接受 Tauri 在原生感上的少量妥协，换取一套代码库覆盖三个平台的巨大效率优势。

### 1.2 四层架构映射

将原生-感架构的四层映射到 Tauri 生态：

```
┌─────────────────────────────────────────────────────────┐
│  Layer 1: Tauri 原生壳（Rust）                           │
│  窗口管理 · 全局热键 · 系统托盘 · 菜单 · 材质            │
│  WebView 生命周期 · 崩溃报告 · 自动更新                   │
├─────────────────────────────────────────────────────────┤
│  Layer 2: WebView + React UI（TypeScript）               │
│  终端渲染 · SFTP 面板 · 监控面板 · AI 侧边栏             │
│  每个窗口类型独立 HTML 入口，独立 JS Bundle                │
├─────────────────────────────────────────────────────────┤
│  Layer 3: Tauri 后端命令（Rust）                          │
│  SSH 连接池 · SFTP 操作 · AI 服务 · 审计日志              │
│  配置管理 · 端口转发 · 监控数据采集                       │
├─────────────────────────────────────────────────────────┤
│  Layer 4: Rust 核心库                                    │
│  russh SSH 协议栈 · rig AI 框架 · 加密存储                │
│  命令安全检查 · 文件索引 · 性能关键路径                    │
└─────────────────────────────────────────────────────────┘
```

### 1.3 IPC 合约设计

**核心原则：一个 schema，多种语言。** 手写编排被禁止。

```
┌──────────────┐    Tauri Commands     ┌──────────────┐
│   React UI   │ ◄══════════════════► │  Rust 后端    │
│  (TypeScript)│    (类型自动生成)      │  (Rust)      │
└──────────────┘                       └──────┬───────┘
                                              │
                                      russh / rig
                                              │
                                              ▼
                                       ┌──────────────┐
                                       │  外部服务     │
                                       │ SSH/AI/存储   │
                                       └──────────────┘
```

**两种 IPC 形态，不可混淆：**

| 形态 | 用途 | 示例 |
|------|------|------|
| **Request/Response** | 带回应的请求 | 连接服务器、执行命令、保存配置 |
| **Events** | 发后即忘的广播 | 终端输出、连接状态变化、AI 流式输出 |

**版本管理**：每条消息携带 schema 版本号。接收方接受同版本或更旧的版本；遇到更新的版本返回 `VersionMismatch`。新增字段必须为 optional。

## 2. 前端设计系统 —— 「墨」设计语言

> 设计哲学：**克制即优雅**。SSH 客户端是生产力工具，不是娱乐应用。视觉应该退到功能后面，让用户的注意力停留在终端输出和运维数据上。

### 2.1 设计原则

| 原则 | 含义 | 实践 |
|------|------|------|
| **静默** | 界面不争夺注意力 | 中性色调，无动画装饰，无渐变背景 |
| **透气** | 信息密度高但不拥挤 | 充裕的留白，合理的分组间距 |
| **一致** | 跨平台视觉统一 | 不模拟任何特定 OS 的外观，走自己的路 |
| **锐利** | 精确的视觉层级 | 2px 以内的间距差异传达层级关系 |
| **深邃** | 深色模式不是简单反转 | 每个灰色层级经过独立调试 |

### 2.5 原生感 CSS 规范

**不可违反的规则**（源自原生感最佳实践）：

```css
/* ❌ 禁止 —— 这是"感觉像网页"的头号标志 */
.hoverable-row { cursor: pointer; }

/* ✅ 正确 —— 原生列表行不改变光标 */
.hoverable-row:hover { background: var(--bg-3); }

/* ❌ 禁止 —— 浏览器默认行为 */
.chrome { user-select: text; }

/* ✅ 正确 —— 只在可编辑内容上启用选择 */
.chrome { user-select: none; }
.editable-content { user-select: text; }

/* ❌ 禁止 —— JS 平滑滚动有弹簧回弹 */
.scroll { scroll-behavior: smooth; }

/* ✅ 正确 —— 原生惯性由 OS 控制 */
.scroll { scroll-behavior: auto; overscroll-behavior: contain; }

/* ❌ 禁止 —— 页面切换应该是瞬时切替 */
.view-enter { animation: fadeIn 0.3s; }

/* ✅ 正确 —— 原生应用不淡入淡出，直接切换 */
.view { display: none; }
.view.active { display: flex; }
```

### 2.6 暗色模式实现

```css

@media (prefers-color-scheme: dark) {
  :root { color-scheme: dark; }

@media (prefers-color-scheme: light) {

```

## 6. 性能策略

### 6.1 启动优化

| 优化项 | 目标 | 实现方式 |
|--------|------|----------|
| 冷启动 | < 800ms | Tauri 预加载 + 按需加载功能模块 |
| 热启动 | < 100ms | 窗口隐藏而非关闭，保留 WebView 状态 |
| 首屏渲染 | < 300ms | 关键 CSS 内联，避免 FOUC |

### 6.2 内存管理

```
目标：空闲状态 < 200MB，活跃使用 < 400MB

策略：
├── 终端输出节流 —— 高频输出限制渲染频率（60fps cap）
├── 文件列表懒加载 —— 只渲染可见区域（虚拟滚动）
├── 连接池回收 —— 空闲 5 分钟的连接自动关闭
├── AI 模型卸载 —— 不使用时释放本地模型内存
├── 窗口销毁 —— 关闭的标签页完全销毁 WebView
└── 后端空闲退出 —— AI 服务空闲 10 分钟后退出进程
```

### 6.3 网络优化

- SSH 连接复用，减少 TCP 握手开销
- 大文件传输分片（64KB chunks），支持断点续传
- 压缩传输（`-C` 选项），减少网络流量
- 异步 IO，所有网络操作不阻塞 UI 线程

## 7. 安全架构

### 7.1 分层安全模型

```
┌─────────────────────────────────────┐
│  用户界面 —— 命令预览与确认          │
├─────────────────────────────────────┤
│  AI 安全沙箱 —— 危险命令拦截         │
├─────────────────────────────────────┤
│  操作审计 —— 全流程日志记录          │
├─────────────────────────────────────┤
│  数据加密 —— OS 密钥环存储          │
├─────────────────────────────────────┤
│  传输安全 —— TLS 1.3 / SSH 加密     │
└─────────────────────────────────────┘
```

### 7.2 危险命令分级

| 级别 | 策略 | 示例 |
|------|------|------|
| 🔴 禁止 | 直接拦截，不允许执行 | `rm -rf /`, `mkfs`, `dd` |
| 🟠 审批 | 显示风险提示，需确认 | `rm -rf ~`, `chmod 777`, `shutdown` |
| 🟡 警告 | 显示警告，可继续 | `sudo apt remove`, `kill -9` |
| 🟢 允许 | 直接执行 | `ls`, `cat`, `grep`, `top` |
